# 🧠 DevOps Basics Cheat Sheet

A standalone reference for every core concept used across this repo: Docker
image optimization, Linux networking, and web infrastructure design. Each
entry is a short plain-English explanation followed by a real-world analogy.

## 🐳 Docker & Image Optimization

- **Docker layer caching** — Docker reuses unchanged steps from a previous build instead of redoing them. Like reheating yesterday's soup instead of cooking it from scratch — only the parts you actually changed get remade.
- **Multi-stage builds** — One Dockerfile stage compiles the app with all its build tools, then a second, minimal (sometimes empty, `scratch`) stage copies over only the finished binary. Like a construction site handing over the finished house while the scaffolding, cement mixer, and sawdust stay behind at the yard.
- **`.dockerignore` & build context filtering** — A list of files and folders excluded from the build context *before* it is even sent to the Docker daemon (`.git`, logs, local secrets, big local-only data), so `COPY`/`ADD` can never see them at all. Like leaving your junk drawer out when you photograph a room for a listing — it never even makes it into the shot, let alone the sale.
- **Layer immutability & "whiteout" deletes** — Once a layer is committed, its bytes are baked in forever; deleting a file in a later `RUN` only hides it, it doesn't shrink the image. Like shredding a document after mailing a copy — the copy already left the building, no matter what you do to the original.
- **Collapsing RUN steps** — Combining create/use/delete into one `RUN` instruction means only the final state is ever committed to a layer. Like packing and unpacking a suitcase in a single motion so the mess never actually gets photographed.
- **Base image selection** — Choosing the smallest base image that still satisfies real runtime requirements. Alpine (musl libc, BusyBox) is often 5-10x smaller than Debian slim or Ubuntu, but musl isn't ABI-compatible with glibc, so anything needing glibc-linked native code should stay on Debian/Ubuntu even though it's larger. Like picking the smallest toolbox that still has every tool the job actually needs — but knowing some jobs genuinely need the bigger toolbox.
- **Image tag vs. digest** — A tag (`alpine:3.22`) is a movable label that can be repointed; a digest (`@sha256:...`) pins one exact, immutable image. Like the difference between "meet me at the coffee shop" (which could change owners) and a GPS coordinate that never moves.
- **Dependency-cache-friendly instruction ordering** — Copying manifest files (`package.json`, `go.mod`) and running the install step *before* copying the rest of the source means an unrelated source edit can't invalidate the expensive install layer. Like a mechanic who bolts the engine block in first and leaves the license plate for last — swapping the plate never means pulling the engine back out.
- **Non-root runtime user** — Setting `USER` to an unprivileged UID so the container doesn't default to running as `root`. Like giving a hotel guest a key that only opens their own room instead of a master key to the whole building — if that key is ever copied, the damage stays contained to one room.
- **Measure before you optimize** — Using `docker image history` and `docker image inspect` to find which layer is actually the biggest, instead of guessing. Like a doctor ordering bloodwork before prescribing treatment — you fix what the numbers show is actually broken, not what merely looks suspicious.

## 🌐 Linux Networking

- **Interfaces & link state (`ip -br addr` / `ip -br link`)** — Lists a host's own network interfaces, their IP addresses, and whether each link is up or down. Like checking which doors and windows your own house actually has, and whether each one is open or shut, before worrying about who's out on the street.
- **Default route (`ip route show default`)** — The one gateway a host sends traffic through when it doesn't have a more specific route to the destination. Like the single driveway connecting a house to the public road — every trip off the property starts by pulling out onto that same driveway, whatever the final destination.
- **ARP / neighbor table (`ip neigh`)** — The host's own memory of which IP address maps to which physical (MAC) address on the local network. Like an apartment building's lobby directory mapping resident names to actual door numbers.
- **Listening TCP sockets (`ss -tln`)** — Shows which local ports have a process actively waiting for incoming connections. Like walking a row of shop counters to see which ones are actually staffed and open for business right now, versus closed with the lights off.
- **Hostname resolution (`getent hosts`)** — Looks up the IP address a given hostname currently resolves to, using the same resolution path the OS itself uses. Like looking up a name in a phone book to find the actual number to dial.
- **Loopback / connectivity test (`ping`)** — Sends packets to a host's own address to confirm its network stack is alive and responding before testing anything external. Like clapping your hands next to your own ear to make sure your hearing works before trying to have a conversation across the room.

## 🧱 Docker Compose

- **Service vs. container** — A service is the *declared intent* in `docker-compose.yml` (image, env, network); a container is the *running instance* Compose creates from it. Like a restaurant's job posting for "cashier" versus the actual person standing at the register — the posting can spawn one cashier or three identical ones without being rewritten.
- **User-defined networks as trust boundaries** — Services only reach each other if they share a Compose network; attaching a service to a network is a deliberate choice, not a default. Like handing out office keycards per floor — being in the building doesn't mean every door opens for you.
- **Service discovery by name** — Compose gives every service a DNS entry matching its name, so `PGHOST: db` resolves without ever touching an IP. Like dialing a coworker by their office extension instead of memorizing which desk phone happens to be wired to which line this week.
- **Named volumes & `down` vs. `down -v`** — A named volume persists data on the host independently of any one container's lifecycle; `docker compose down` removes containers but leaves the volume, while `down -v` deletes it too. Like a filing cabinet that survives an office remodel — unless someone explicitly orders it hauled to the dump.
- **`.env` / `.env.example`** — Real secrets and config live in a git-ignored `.env` file the Compose file merely references; `.env.example` documents the required keys with placeholder values so the repo stays runnable without leaking anything real. Like a recipe card that lists "1 secret ingredient (see pantry note)" instead of printing grandma's actual formula for everyone to read.
- **Start order vs. readiness (`depends_on: condition: service_healthy`)** — A container *starting* only means its process began; a healthcheck confirms it can actually serve requests. `depends_on` with `service_healthy` blocks a dependent service until the healthcheck passes, not just until the container exists. Like a chef waiting for the oven's ready light, not just the moment someone plugged it in.
- **Healthcheck fields (`interval`, `timeout`, `retries`, `start_period`)** — `interval` sets how often the probe runs, `timeout` how long one attempt may take, `retries` how many consecutive failures before "unhealthy," and `start_period` a grace window where early failures don't count against that total. Like a new employee's probation period — early stumbles are expected and don't count against them the way a mistake would a year in.

## 🏗️ Web Infrastructure Design

- **DNS & the A record** — DNS translates a human-readable domain name into an IP address; an A record maps a name directly to an IPv4 address. Like a store's listing on a map app showing its exact street coordinates, rather than a forwarding note that says "ask the mall directory for the real address" (that indirection is closer to what a CNAME does).
- **TCP/IP as reliable transport** — IP addresses and routes packets between two machines; TCP on top of it guarantees the data arrives in order and without loss. Like registered mail with tracking and numbered envelopes — IP gets the envelope roughly to the right building, TCP is the numbering and confirmation system that guarantees every envelope arrives, and in the right order.
- **LAMP / LAMP-like stack** — LAMP names a classic layering: Linux, Apache, MySQL, PHP. A stack is "LAMP-like" when it keeps that same shape (OS, web server, database, app code) but swaps a piece, e.g. Nginx instead of Apache. Like a recipe name such as "Margherita pizza" — swap the cheese brand or the oven and it's still recognizably a Margherita, even if it's not the exact original recipe.
- **Single point of failure (SPOF)** — Any one component whose failure takes down the whole system because nothing else can pick up its job. Like a tightrope walker working without a net — one slip and there's nothing left standing between the act and disaster.
- **Load balancing, redundancy & round robin** — Spreading traffic across multiple identical servers so no single machine is a SPOF; round robin is a simple distribution method that sends each new request to the next server in line, wrapping back to the first once it reaches the last, and needs no explicit directive since it's the Nginx `upstream` default. Like a restaurant with several cash registers open at once, seating each new customer at the next free register in turn instead of forcing everyone through one line.
- **Layer 4 vs. Layer 7 load balancing** — An L4 balancer routes on transport-layer info alone (IP/port, TCP/UDP) without reading the request itself; an L7 balancer terminates HTTP and can route, rewrite, or retry based on path, headers, or cookies. Like a mailroom that sorts packages by street address alone (L4) versus a mailroom clerk who actually opens the envelope to route it by what's written inside (L7).
- **Least-connections, weighted, and hash-based balancing** — `least_conn` sends the next request to whichever backend has the fewest open connections, better when request cost varies; `weight=N` skews round robin toward specific servers (uneven hardware, canary releases); hash-based (`ip_hash`, `hash $key`) deterministically pins a given key to the same backend every time, useful for cache locality without shared state. Like, respectively: seating the next customer at whichever register's line is shortest right now, giving the fast register more customers per rotation on purpose, and always sending the same regular customer to the cashier who already knows their usual order.
- **Backup servers** — A server flagged `backup` in an `upstream` block receives zero traffic while any non-backup server is healthy, and only activates once all of them are down. Like a spare tire in the trunk — never used on a normal drive, only bolted on when every good tire has already failed.
- **Active-active vs. active-passive** — In active-active, all redundant nodes handle real traffic simultaneously; in active-passive, one node handles everything while the other sits idle, ready to take over only on failure. Like two cashiers both ringing up customers at once, versus one cashier working the register while a second waits in the break room, stepping in only if the first collapses.
- **Passive vs. active failure detection** — Passive detection only learns a backend is down when a real client request is routed to it and fails (cheap, but the failing request pays the discovery cost); active detection has the balancer independently probe each backend on its own schedule, catching failures before any client request hits them (extra dedicated traffic and infrastructure). Like finding out a shop is closed only when a customer walks up to a locked door (passive), versus a security guard doing scheduled rounds checking every storefront before customers ever show up (active).
- **`max_fails` and `fail_timeout`** — `max_fails` is the failure-count threshold before Nginx marks an upstream down; `fail_timeout` is the time window during which that count accumulates *and* how long the upstream then stays marked down before being retried — it's a memory window, not a clock that discovers failures on its own. Like a three-strikes rule at a bar: strikes only count when the bouncer actually catches something (passive), and after being cut off, a patron simply isn't allowed back in until a fixed cool-down has passed.
- **Sticky sessions vs. shared session state** — Sticky sessions pin one client to one backend (by cookie or IP hash) so session data kept in that instance's memory stays reachable, but break if that instance goes down; shared session state (session data in a database/cache instead of instance memory) lets any backend serve any client, which is what lets a stateless pool tolerate losing any one member. Like a regular being seated at the same waiter's table every visit because that waiter remembers their order by heart (sticky), versus every order being written on a shared ticket rail any waiter in the kitchen can read (shared state).
- **Connection draining** — Letting a backend being removed finish its in-flight requests normally while new requests go elsewhere, instead of cutting it off mid-response. Like flipping a checkout lane's sign to "closing" — the customer already in line still gets rung up, but no one new joins that line.
- **Database primary/replica & replication** — The primary is the only node the application writes to; the replica is a copy kept in sync through replication, a one-way flow of changes from primary to replica. Like an original ledger and a photocopier fed every new entry the instant it's written — the copy is great to read from, but the original is still the only book anyone may write new entries into.
- **Tiered web architecture (web / app / database)** — Splitting a stack into independently scalable layers, each fronted by redundancy, instead of running everything on one box. Like a restaurant separating the dining room, kitchen, and pantry so each can be staffed and expanded on its own schedule.
- **Firewall** — Inspects traffic at the network/transport level and allows or blocks it by rules like source, destination, and port — it does not read or understand application-level content. Like a building's security guard who checks ID badges at the door but never opens the envelope a visitor is carrying.
- **HTTPS / TLS encryption** — Wraps HTTP traffic in TLS so it can't be read or altered in transit, and lets the client verify it's really talking to the intended server. Like agreeing on a private code language at the start of a phone call, so anyone tapping the line hears only gibberish and you can be sure you're actually talking to who you think you are.
- **TLS termination** — The point in the infrastructure (e.g. the load balancer) where encrypted traffic is decrypted; anything past that point travels in the clear unless it's deliberately re-encrypted. Like an armored truck that only guards the cash from the bank to the depot's front gate — once inside, it may ride an unmarked cart between rooms, which is fine only if everyone inside the building can be trusted.
- **Monitoring & QPS** — Agents on each component expose metrics (requests handled, response times, resource usage) that a monitoring system collects; QPS (queries per second) tracks load over time. Like a car's dashboard gauges — speedometer, temperature, fuel — that let a driver spot trouble before it strands them on the highway.
